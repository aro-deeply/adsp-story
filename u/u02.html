편의점 사장님, 엑셀 지옥에서 창고를 짓다

1장에서 영수증으로 답을 찾던 사장님이 2호점, 3호점을 냈어요. 지점마다 엑셀 파일이 따로 놀고 숫자가 서로 안 맞기 시작해요. 2장은 모두가 같이 쓰는 잘 정리된 창고(데이터베이스)를 짓고, 그 창고를 목적별로 나눠 쓰는 이야기예요.

이 단원 전체를 한 문장으로흩어진 엑셀 대신 하나의 창고(DB)를 순서대로 설계하고(개논물), SQL로 말을 걸고, 커지면 계산대용(OLTP), 분석용(OLAP, 웨어하우스), 뭐든 다 붓는 호수(레이크)로 나눠 쓴다.

PART 1 · 창고 짓기 (3쪽)

1화

지점마다 엑셀이 따로 노는 지옥

3쪽
한 줄 핵심1호점 파일엔 단골 김씨가 "010-1234", 2호점 파일엔 "010-9999". 어느 게 맞지? 이 혼란을 끝내려면 창고가 같이 쓰이고, 하나로 합쳐 있고, 저장돼 있고, 바뀌어도 정확해야 한다. 이게 DB의 4특징.
DB 전 · 지점별 엑셀

같은 손님이 세 군데에

1호점: 김OO 010-1234
2호점: 김OO 010-9999
3호점: 김OO (번호 없음)

중복, 서로 다름, 누가 고쳤는지 모름

DB 후 · 창고 하나

손님 한 명 = 기록 한 줄

모든 지점이 같은 창고를 봄
번호를 바꾸면 모든 지점에 바로 반영

중복 없음, 늘 최신, 늘 정확

DB 특징뜻사장님 가게에서
공용 데이터여러 사용자가 다른 목적으로 같이 씀점장은 재고, 사장님은 매출, 본사는 회계를 같은 창고에서
통합된 데이터같은 데이터가 중복되지 않음김씨 기록은 딱 한 줄
저장된 데이터컴퓨터가 접근할 수 있는 저장 매체에 저장공책이 아니라 서버에
변화되는 데이터추가, 수정, 삭제가 있어도 정확한 현재 상태 유지새 손님, 번호 변경, 탈퇴가 매일 있어도 정확
무결성 (Integrity)데이터가 틀림없이 정확하게 유지되는 성질. "변화되는 데이터"의 목표.
정보 축적·전달 측면 가치기계가독성(컴퓨터가 읽을 수 있음), 검색가독성(원하는 것을 바로 찾음), 원격조작성(멀리서도 다룸). 공책 장부엔 없는 장점 3가지.
"휘발성 데이터"는 DB 특징이 아니에요. 5화의 데이터 웨어하우스는 오히려 비휘발성이 특징이라, 둘을 섞은 보기가 나와요.
공통저변 (공통의 저변): 공용, 통합, 저장, 변화.
2화

창고는 어떤 순서로 짓나

3쪽
한 줄 핵심집 짓기와 같다. 뭘 원하는지 듣고 → 스케치 → 상세 도면 → 실제 공사. 머릿속 그림에서 점점 기계 쪽으로 구체화되는 순서라서 거꾸로 할 수가 없다.
요구조건 분석무엇이 필요?"손님, 상품, 주문을 관리하고 싶어요" 듣기
① 개념적 설계스케치손님이 주문을 한다, 주문에 상품이 담긴다 → ERD, 개념 스키마
② 논리적 설계상세 도면손님 표, 주문 표의 칸(열)과 연결 규칙 정하기 → 논리 모델링
③ 물리적 설계실제 공사어느 디스크에, 어떤 저장 구조로, 인덱스는 어디에

요구조건 분석 → 개념 → 논리 → 물리  ·  사람의 말에서 기계의 저장 구조로

ERDEntity Relationship Diagram. "손님", "주문" 같은 대상(개체)과 그 사이 관계를 그린 스케치 그림. 개념적 설계의 결과물.
논리 모델링스케치를 표(테이블) 구조로 옮기는 작업
물리적 설계실제 저장 장치에 어떻게 저장할지(저장 구조, 접근 방법) 정하기
개논물 (개가 논물을 마신다). 그리고 맨 앞엔 늘 요구조건 분석. "듣고, 스케치하고, 도면 그리고, 공사한다."
3화

창고지기와 창고에 말 거는 언어

3쪽
한 줄 핵심창고를 관리하는 프로그램이 DBMS, 창고에 일을 시키는 말이 SQL. SQL은 "창고 틀을 만들어"(DDL), "물건 넣고 빼"(DML), "출입 권한 줘"(DCL)로 나뉜다.
표로 정리하는 창고

관계형 DBMS

모든 걸 행과 열의 표(테이블)로 저장하고 표끼리 연결.

MySQL, MariaDB, Oracle

표에 안 맞는 것도 담는 창고

NoSQL

리뷰, 사진 정보처럼 비정형 데이터를 저장, 처리. 표 규칙이 느슨함.

HBase, MongoDB, Redis, Cassandra

DDL정의어 · 틀
CREATEALTERDROP

"손님 표를 만들어, 칸 하나 바꿔, 표를 없애." 표 자체를 다룸.

DML조작어 · 내용물
SELECTINSERTUPDATEDELETE

"김씨 기록 찾아, 새 손님 넣어, 번호 고쳐, 탈퇴 손님 지워." 표 안의 줄(행)을 다룸.

DCL제어어 · 권한
GRANTREVOKE

"2호점 점장에게 열람 권한 줘, 그만둔 알바 권한 뺏어."

창고 안내판들: 헷갈리는 네 단어

스키마창고의 설계도. DB 구조와 제약조건(규칙)을 적은 명세.
메타데이터데이터를 설명하는 데이터. 예: 사진의 촬영 날짜, "이 칸은 전화번호, 11자리".
데이터 사전메타데이터를 모아 둔 저장소.
인덱스책 뒤 색인처럼 빨리 찾게(정렬, 탐색) 돕는 보조 도구.
SELECT는 "조회"라서 DML이 아닐 것 같지만 DML이에요. CREATE는 표 자체를 만드니 DDL. COMMIT, ROLLBACK(작업 확정, 되돌리기)은 TCL로 따로 나누기도 하고 DCL에 넣는 교재도 있어요. 권한 GRANT, REVOKE는 어디서나 DCL.
DDL은 틀(Definition, 정의), DML은 내용물(Manipulation, 조작), DCL은 권한(Control, 제어). 가운데 글자만 보면 돼요.

PART 2 · 창고를 목적별로 나눠 쓰기 (3~4쪽)

4화

계산대 창고와 사무실 창고는 다르다

3쪽
한 줄 핵심지점이 10개가 되자 문제가 생겼다. 사장님이 무거운 분석을 돌리면 계산대 결제가 느려진다. 그래서 "지금 거래 처리용"(OLTP)과 "쌓인 걸 분석용"(OLAP)을 나눈다. 회사 안 다른 시스템들도 결국 무엇을 관리하느냐로 이름이 붙었다.
계산대 · 지금 이 순간

OLTP

Online Transaction Processing. 다량의 짧은 거래를 실시간 처리.

결제, 주문, 포인트 적립. 한 건은 작지만 쉴 새 없이 많음.

사무실 · 쌓인 기록

OLAP

Online Analytical Processing. 다차원 데이터를 대화식으로 분석.

"지점별 × 월별 × 상품별 매출"을 이리저리 돌려 보기.

이름무엇을 관리하나사장님 가게에서
CRM고객 관계 관리단골 포인트, 생일 쿠폰
SCM공급망 관리납품업체, 물류, 재고 흐름
ERP전사 자원 관리회계, 인사, 재고, 구매를 하나로
RTE실시간 기업본사가 모든 지점 상황을 실시간으로
KMS지식 관리 시스템1장의 발주 매뉴얼을 모아 공유
BI리포트 중심 도구"지난달 매출 보고서" (무슨 일이 있었나)
BA통계 기반 통찰, 예측까지"다음 달 어디가 잘 팔릴까" (BI보다 한 걸음 앞)
블록체인참여자 모두가 정보를 분산 저장장부를 한 곳이 아니라 모두가 나눠 들고 있음
OLTP의 T = Transaction(거래), OLAP의 A = Analytical(분석). 글자 하나로 끝나요. BI는 "과거 보고서", BA는 "미래까지 분석".
5화

본사의 기록 보관소, 데이터 웨어하우스

4쪽
한 줄 핵심지점 DB, 납품 DB, 고객 DB가 다 따로라 "지난 3년 전체 흐름"을 볼 수가 없다. 그래서 분석용으로 한곳에 모아 정리해 둔 중앙 창고(DW)를 만든다. 넣는 과정이 ETL, 넣기 전 잠깐 쌓아 두는 곳이 ODS.

주제지향성

"매출", "고객"처럼 분석 주제별로 정리. 계산대처럼 업무 순서대로가 아님.

통합성

지점마다 "남/여", "M/F"로 다르던 표기를 하나로 맞춰 모음.

시계열성

지난 3년, 5년의 과거 이력을 시간 순으로 보관.

비휘발성

한 번 넣으면 수시로 고치지 않는 읽기 전용 기록 보관소.

ETLExtract(추출) Transform(변환) Load(적재). 데이터를 옮기는 과정.
ODSOperational Data Store. 여러 DB에서 뽑은 데이터를 DW에 넣기 전 임시로 저장하는 곳.
ETL은 과정, ODS는 장소. "임시로 저장하는 곳은?" 하면 ODS예요. 그리고 DW는 비휘발성. "휘발성"이 들어간 보기는 오답.
주통시비: 주제, 통합, 시계열, 비휘발. 1화 DB 특징 공통저변과 짝으로 외워요. DB는 매일 바뀌는 "변화", DW는 안 바뀌는 "비휘발".
6화

사진, 리뷰, 영상은 어디에 담나

4쪽
한 줄 핵심웨어하우스는 정리해서 넣느라 손이 많이 가고, 리뷰 사진이나 CCTV 영상은 표에 맞지도 않는다. 그래서 모양 상관없이 원본 그대로 일단 다 붓는 호수(데이터 레이크)가 생겼다. 너무 커서 컴퓨터 한 대로 못 다루니 여러 대를 묶는 하둡.
정리된 창고

데이터 웨어하우스

정형 데이터를 정리, 변환해서 주제별로 보관. 분석 준비 완료 상태.

모든 걸 받는 호수

데이터 레이크

정형, 반정형, 비정형을 원본 그대로 모두 저장. 쓸 때 꺼내서 가공.

나눠서 저장하는 것 = HDFS · 나눠서 동시에(병렬) 처리하고 합치는 것 = MapReduce

하둡 (Hadoop)여러 컴퓨터를 묶어 대용량을 처리하는 오픈소스
HDFS분산 파일 저장 (여러 컴퓨터에 나눠 담기)
MapReduce분산된 데이터를 병렬 처리 (나눠서 동시에 계산하고 합치기)
요약노트에 데이터 레이크가 "비정형 저장소"라고만 적혀 있다면, 정확한 설명은 정형, 반정형, 비정형 모두를 원본 그대로예요. 시험 보기도 이쪽이 정답이에요.
HDFS의 FS = File System(저장), MapReduce는 나눠서(Map) 모아 줄인다(Reduce) = 처리. 웨어하우스는 정리된 창고, 레이크는 다 받는 호수.
끝

확인 8문제

답을 떠올려 본 뒤 눌러서 확인하세요. 5개 이상 떠오르면 오늘은 충분해요.

DB의 4특징은? "휘발성"은 들어가나?

공용, 통합, 저장, 변화(공통저변). 휘발성은 없어요. DW는 반대로 비휘발성.

같은 데이터가 중복되지 않는다는 DB 특징은?

통합된 데이터. 김씨 기록은 딱 한 줄.

DB 설계 순서는?

요구조건 분석 → 개념적 → 논리적 → 물리적(개논물). 듣고, 스케치, 도면, 공사.

SELECT, INSERT, UPDATE, CREATE 중 DML이 아닌 것은? GRANT는?

CREATE는 틀을 만드는 DDL. GRANT는 권한이라 DCL.

MongoDB, Redis, Oracle, Cassandra 중 NoSQL이 아닌 것은?

Oracle. 관계형 DBMS예요.

결제, 주문 같은 짧은 거래를 실시간 처리하는 시스템은?

OLTP(T = Transaction). 분석은 OLAP.

DW의 4특징과, 넣기 전 임시 저장소의 이름은?

주제지향, 통합, 시계열, 비휘발(주통시비). 임시 저장소는 ODS. ETL은 옮기는 과정.

데이터 레이크의 정확한 설명과, 하둡에서 병렬 처리를 맡는 기술은?

레이크 = 정형, 반정형, 비정형 모두 원본 그대로. 병렬 처리는 MapReduce(저장은 HDFS).

2장 한 문장

흩어진 엑셀을 공통저변의 창고(DB)로 바꾸고, 개논물 순서로 설계해 SQL(DDL 틀, DML 내용물, DCL 권한)로 다룬다. 커지면 계산대용 OLTP와 분석용 OLAP을 나누고, 주통시비 보관소(DW)와 뭐든 받는 호수(레이크, 하둡)를 둔다. 그런데 앱 주문, SNS 리뷰, 매장 센서까지 데이터가 홍수처럼 밀려오는데… 다음 장, 빅데이터.
